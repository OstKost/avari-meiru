# Диагностика таймаута повторного подключения

Дата: 2026-11-11. Проверялся только локальный mixed-клиент без TUN, без root и без изменения маршрутов или AWG. Исходники не менялись. Повторный live TUN не запускался.

## Окружение на момент проверки

- Default-маршрут Mac: `utun7` (AWG), адрес `172.16.17.6`, MTU 1280. Маршрут к `31.58.213.192` тоже через `utun7`. Физический `en1`: `192.168.68.101`, MTU 1500, в журнале ядра index 15.
- Обычный `curl` без прокси: `https://icanhazip.com` → `109.107.176.224`, `https://example.com` → HTTP 200. Тот же внешний IP сохранился после всех проб.
- `curl --interface en1` к `https://icanhazip.com` → `185.216.193.116`. Прямой выход через `en1` в целом живой.
- TCP к `31.58.213.192:28443` устанавливается примерно за 0,07 с и с default (`172.16.17.6`), и с `IP_BOUND_IF` на `utun7` (index 27), и с `IP_BOUND_IF` на `en1` (index 15).
- Процессов Mieru, supervisor и sing-box в начале и в конце не было. `utun8` нет.
- VPS по SSH, только чтение: `mita` 3.38.0, `mita status` = RUNNING, `mita.service` active/running, `*:28443` слушает процесс `mita`. UFW inactive, отдельных правил iptables для 28443 нет. Служба не перезапускалась. Время VPS в этой проверке: `2026-11-11T19:06:31Z`.
- Профиль `~/Library/Application Support/Mieru/profile.json` побайтно совпадает с `vps-test-profile.json` (оба `0600`): сервер `31.58.213.192`, порт `28443`, транспорт TCP, поля `traffic_pattern` нет.

Строка ядра `network: updated default interface en1` — это монитор физического интерфейса. Она пишется и когда исходящий сокет реально идёт через `utun7`. Интерфейс dial нужно смотреть по локальному адресу сокета, а не по этой строке.

Прошлые TUN-сессии уже содержали ту же строку и для успешного прохода (`utun8`, без socks5 TIMEOUT), и для сбойного (сессия `9a776849…`: 145 строк `failed to read socks5 connection response from the server: TIMEOUT`, в том числе mixed к `icanhazip.com:443`). Одного выбора `en1` в журнале недостаточно, чтобы объяснить, почему первый TUN прошёл, а следующий нет.

## Как проверялось

Закреплённый `core/dist/sing-box-aarch64-apple-darwin`. Временные JSON только inbound `mixed` на `127.0.0.1` (порты 12170–12173), outbound `mieru`, `route.final=mieru-out`. Каталог вне репозитория, режим конфигов `0600`, после проб каталог удалён. Клиенты останавливались `SIGTERM`. AWG, таблица маршрутов и сервер не изменялись.

| `auto_detect_interface: true`, первый процесс | `192.168.68.101` (`en1`), на раннем сэмпле `SYN_SENT` | curl 28, timeout около 8 с | HTTP `000`, curl 28. | `auto_detect_interface: true`, второй процесс | состояние сокета `SYN_SENT` → `ESTABLISHED` | `31.58.213.192`, код 0 | не запрашивался отдельно |

На сервере вокруг успешных проб `PassiveOpens` вырос, счётчики расшифрования выросли, `HandshakeErrors` остался 0, `FailedDirectDecrypt` остался 0. Имя пользователя в этот документ не переносилось.

## Вывод

Устойчивая причина таймаута не доказана. `auto_detect_interface: true` действительно уводит dial на физический `en1`, и один такой процесс воспроизвёл точный socks5 TIMEOUT. Сразу после этого три новых процесса с тем же `true` прошли через `en1` и вернули IP VPS. `false` и явный `bind_interface=utun7` тоже вернули `31.58.213.192`. Прямой путь `en1` сейчас не закрыт: и обычный TCP на 28443, и полный handshake Mieru через него проходят. Гипотеза «auto_detect обходит AWG, и прямой путь недоступен» этими пробами не подтвердилась.

Успех loopback не доказывает повторный TUN. В TUN-конфиге нельзя просто выключить `auto_detect_interface`: без привязки исходящий сокет пойдёт по новому default, то есть в сам туннель.

## Что не делать и что осталось

Исходники не менять по этому результату. AWG не отключать. Сервер не перезапускать.

Следующий live TUN — только координатор. Имеет смысл смотреть локальный адрес сокета к `31.58.213.192:28443`, а не строку `default interface en1`. Если таймаут снова совпадёт с сокетом на `en1`, узкая следующая проба — один TUN-конфиг с `bind_interface` на интерфейс, который был default до TUN (сейчас `utun7`). На loopback такой bind уже дал IP VPS и HTTP 200; под TUN это ещё не проверялось.

## Последующий live TUN

Координатор повторил полный TUN без изменения кода и без отключения AWG: внешний IP VPS 31.58.213.192, HTTPS200. Также прошли скрытие/возврат окна и аварийная очистка после SIGKILL GUI. Подробности в [MACOS_SMOKE.md](MACOS_SMOKE.md). Этот успех не устанавливает причину ранее наблюдавшегося таймаута и не доказывает длительную стабильность.
