# Проверка сохранённого сервера

Команда `server_health_check` без аргументов проверяет уже сохранённый профиль. UI не передаёт адрес, порт и учётные данные. Пароль остаётся в процессе backend: его нет в ответе, журнале и аргументах процесса.

Проверка не включает VPN, не поднимает TUN, не меняет маршруты и не пишет пользовательский профиль или активную сессию.

## Контракт

```rust
pub async fn check(state: crate::vpn::AppState) -> Result<health::ServerHealth, String>
```

`Ok` — обычный результат со статусом. `Err` — только сбой самого вызова (задача проверки оборвана), короткой русской фразой без секрета и без stderr.

```json
{
  "state": "ready",
  "latency_ms": 842,
  "message": "Сервер отвечает",
  "checked_at": "2026-11-11T12:00:00.000Z"
}
```

`state`: `ready`, `error`, `unconfigured`, `busy`. `latency_ms` — миллисекунды или `null`. `checked_at` — UTC RFC3339. `latency_ms` заполнен только при `ready`.

| state | когда | latency_ms | message |
| --- | --- | --- | --- |
| `unconfigured` | файл профиля отсутствует | `null` | Сервер не настроен |
| `busy` | проверка уже идёт | `null` | Проверка уже выполняется |
| `ready` | через ядро пришёл ответ HTTP | миллисекунды | Сервер отвечает |
| `error` | профиль повреждён, ядро не найдено, отказ, таймаут или ответ не HTTP | `null` | см. ниже |

Остальные тексты `error`: «Сохранённый профиль некорректен», «Не удалось подготовить проверку», «Ядро не найдено», «Ядро проверки остановилось», «Сервер отклонил соединение», «Ответ сервера не распознан», «Сервер не ответил вовремя». Сырой stderr ядра наружу не отдаётся.

Команда IPC `server_health_check` без аргументов вызывает `health::check`. Разрешение `allow-server-health-check` описано в `permissions/server_health_check.toml` и подключено в capabilities. Список имён в `build.rs` это разрешение не создаёт: его читает сканер каталога `permissions`.

На macOS профиль читает `vpn::load_saved_profile`: тот же `profile.json`, что и экран профиля (`~/Library/Application Support/Mieru/profile.json`). На Linux `vpn_linux.rs` этим изменением не трогается; модуль сам собирает тот же путь, что Linux VPN: `$XDG_DATA_HOME/mieru/profile.json` или `~/.local/share/mieru/profile.json`.

## Что измеряется

Фиксированная цель: `example.com:80`, запрос `GET / HTTP/1.1` с `Host: example.com`. Успех — разобранная строка состояния `HTTP/1.0` или `HTTP/1.1` с кодом 100–599. Это ответ через сервер, не ICMP и не имя «ping».

`latency_ms` считается от начала TCP-соединения к loopback mixed до чтения этой строки. Старт процесса ядра в цифру не входит.

Цепочка: временный rootless `sing-box run` с одним mixed inbound `127.0.0.1` и outbound `mieru` из сохранённого профиля, затем SOCKS5h (домен `example.com` уходит в ядро, GUI его не резолвит). DNS цели — `1.1.1.1` через `detour: mieru-out`. `route.final` — `mieru-out`, `auto_detect_interface` — true, чтобы сокет к серверу не ушёл в уже поднятый TUN. В конфиге нет `tun`, `auto_route`, `auto_redirect`, `interface_name`.

Имя сервера из профиля пишется в outbound как есть. Резолвит его дочерний процесс, не GUI. Для TCP закреплённое ядро отдаёт имя своему dialer. Для UDP у mbox `NilDNSResolver`: домен в UDP outbound при наборе не резолвится, `check` такой конфиг принимает, а пробник завершится ошибкой. Обход — сохранить в профиле IP. Отдельный TCP-коннект к UDP-порту сервера не выполняется и успехом не считается.

Готовность ядра — строка stderr `sing-box started (` при живом процессе. Маркер совпадает с VPN-сессией.

Такая проверка подтверждает обмен через ядро, авторизацию и выход на сервер. Она не доказывает системные маршруты TUN и не является проверкой утечек.

## Срок и одна проверка

Жёсткий срок пробника — 8 секунд, включая старт ядра, ожидание готовности и HTTP. Каждый сокетный таймаут ограничен остатком этого срока. `check` выполняет работу в `spawn_blocking`, цикл UI Tauri не блокируется.

Одновременно выполняется один пробник. Второй вызов сразу получает `busy` и не встаёт в очередь. Повторов в фоне нет.

Свой VPS и боевой профиль тестами не читаются. Живую сетевую приёмку делает координатор отдельно.

Для отдельной ручной сетевой проверки есть игнорируемый по умолчанию тест:

```bash
cargo test --offline --manifest-path desktop/src-tauri/Cargo.toml --lib saved_server_live_smoke -- --ignored --nocapture
```

Он читает сохранённый профиль через backend, выводит только безопасный `ServerHealth`, не запускает TUN и ожидает `ready`. Обычные тесты его не выполняют. Первая попытка координатора 2026-11-12 вернула `error` при недоступном VPS. После повторной активации сервера пользователем тест прошёл: `ready`, 236 мс. Автоматическая проверка в нативном приложении также прошла: 244 мс, затем 233 мс после перезапуска. Секреты в результаты не включались.

## Процесс и файлы

Каталог пробника — частный `0700` под временным каталогом ОС. Имя — `mieru-health-<pid>-<случайные байты>`. Конфиг — `0600`. Пароль лежит только в этом файле. Каталог не находится в сессии VPN.

Ядро запускает `/bin/sh`, а не GUI напрямую. У оболочки своя группа процессов. Её stdin — канал, который держит приложение; `sing-box` получает stdin из `/dev/null`, чтобы не забрать этот канал. Конец канала читает фоновый `cat <&0`. Явное перенаправление нужно потому, что неинтерактивный bash иначе подменяет stdin фоновой команды на `/dev/null`, и оболочка приняла бы это за закрытие канала. Пароль в окружение и в текст скрипта не подставляется. Отдельного фонового `sleep` нет: и предел в 9 секунд, и пауза между `SIGTERM` и `SIGKILL` — это передний `sleep 1`, который завершается вместе с оболочкой.

Очистка оболочки одна и та же при EOF канала, при `EXIT` и при `INT`/`TERM`/`HUP`. Сначала она собирает своего читателя stdin. Затем, только если ppid ядра всё ещё эта оболочка, шлёт `SIGTERM`, ждёт одну секунду и, если это всё ещё её ребёнок, шлёт `SIGKILL`, после чего делает `wait`. Pid, который уже не её ребёнок, сигнал не получает. Каталог удаляется только если после `wait` процесса уже нет: путь абсолютный, без `..`, это каталог и не симлинк, последняя компонента начинается с `mieru-health-` и цифры и состоит из `[A-Za-z0-9-]`. Если процесс всё ещё жив, каталог остаётся. Другие каталоги команда не затрагивает.

Нормальный конец, ошибка и отмена идут через RAII. Сначала запоминаются pid ядра и метка его старта. Группе живой оболочки уходит `SIGTERM`, затем ожидание до 400 мс. `SIGKILL` группы посылается только пока эта оболочка ещё не собрана: после `wait` тот же идентификатор группы мог достаться другому процессу. Если pid ядра всё ещё несёт ту же метку старта, этот pid получает `SIGTERM`, короткую паузу и `SIGKILL`, снова только пока метка совпадает. Затем каталог удаляет и Rust.

Если приложение зависло и канал открыт, та же последовательность `SIGTERM`, одна секунда, `SIGKILL` начинается не позже чем через 9 секунд.

Практический предел: `SIGKILL` самой оболочки не выполняет trap и не запускает ни эскалацию, ни удаление каталога. Если в этот момент GUI тоже уничтожен `SIGKILL`, деструктор Rust не выполняется. Ядро, которое проигнорировало уже посланный `SIGTERM` и вышло из группы, может остаться, и каталог с паролем тоже. Обычный `sing-box run` группу не покидает и не демонизируется. Пока оболочка жива, `SIGKILL` её группы убивает и ядро.

Оболочка нужна потому, что у macOS нет `PR_SET_PDEATHSIG`, а `fork` из многопоточного Tauri без немедленного `exec` небезопасен. Скрипт рассчитан на `/bin/sh` macOS и Linux (`set -u`, без `read -t`).
