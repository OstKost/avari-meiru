# План финального Linux-выпуска

Согласовано: локальные пакеты и настоящая desktop-приёмка; публикация, подписи, AUR, AppImage и Flatpak вне этого этапа. Цели — Ubuntu 24.04, Debian 13 и Arch x86_64. Реализация разрешена пользователем после составления плана, новыми Antigravity workers.

## Результат и исходная база

Существующие GUI/helper, pinned mbox, VPS core/TUN/DNS и Xvfb/localmita сценарии уже проверены. Сохраняем их архитектуру, фиксированные пути helper/core и рабочую macOS-ветку. Открытые пункты — самостоятельная сборка без старого UI dist, согласованное поколение пакетов, standalone Arch recipe и настоящий logind/polkit-сеанс.

## Изменения сборки

- Обычный release build всегда выполняет frozen-lockfile install и актуальную сборку UI. Режим build-only явно допускает reuse существующего dist и записывает это в manifest; исправить неработающее чтение BUILD_ONLY из окружения либо оставить только документированный флаг.
- Allowlist staging включает только исходники и требуемые артефакты, без target/node_modules/caches/профилей. Manifest формируется из staged inputs, а не меняющегося рабочего дерева, для полного и build-only режимов.
- Сохранить Rust 1.98.1 и закреплённый commit mbox. Записать digest использованных Docker images и дату Arch snapshot; не обновлять зависимости ядра. Добавить Cargo caches без зависимости экспорта от скрытого cache-mounted target.
- Дать отдельный pack-only режим из принятого out: одна компиляция GUI/helper → проверка → три пакета. Автоматически сверять извлечённые payload hashes, policy без allow_gui, root ownership и режимы. Выпускать SHA256SUMS и manifest рядом с пакетами.
- Выпускать готовые Arch PKGBUILD и локальный source archive с настоящей checksum; шаблон REPLACE_HASH не выдавать пользователю как самостоятельный рецепт. Сохранять !debug/!strip и точный выбор основного пакета.
- Сборка без git metadata должна работать: текущая папка не является git repository. Связь исходников с артефактами задаётся content manifests.

## Реальная Linux-приёмка

- Подготовить одну одноразовую Ubuntu 24.04 amd64 VM с QEMU TCG на macOS arm64, systemd/logind, X11/Xfce и настоящим polkit-agent. QEMU пока отсутствует; его установка и подготовка VM входят в задачу. Диски/ключи/пароль тестовой VM — только ignored task cache, без изменения пользовательских SSH/VPN настроек. Сеть — user-mode NAT, доступ к консоли/SSH только loopback.
- Войти обычным guest-пользователем через display manager. Установить финальный deb. Проверить отмену настоящего диалога администратора и успешную авторизацию, без правила polkit YES и без root GUI.
- С действующим VPS: baseline → GUI connect → DNS/HTTPS200/внешний IP VPS → disconnect → восстановление сети; один reconnect, hide/show/выход из трея и аварийный GUI exit с отсутствием ядра/TUN. Не повторять расширенные матрицы и прежние headless-тесты без причины.
- Если desktop не предоставляет tray host, проверить доступность выхода и отсутствие скрытого недоступного окна. Исправления только по реально воспроизведённым проблемам, без переписывания UI.
- На Debian/Arch достаточно существующей базовой приёмки пакетов плюс проверки нового payload/зависимостей; при изменениях формата/зависимостей повторить соответствующий install/remove/ldd. Не создавать три полные desktop VM.

## Завершение и интерфейсы

Tauri IPC, профиль JSON и пути установки сохраняются. Новые интерфейсы — build/pack/verify команды и комплект manifest/checksums, описанные в packaging README. После относящихся backend-изменений выполнить cargo check macOS и обязательную Linux-сборку; UI build только при релевантных изменениях или полном clean build.

Обновить итоговый отчёт с фактическими командами, кодами, версией VM и проверенными hashes. Отсутствие VM, интерактивной авторизации или действующего VPS означает незакрытый пункт, а не успех Xvfb. Перед сетевой приёмкой повторно проверять доступность временного сервера. Критерий готовности — три согласованных пакета, воспроизводимые инструкции и успешный native Linux GUI → VPS сценарий с восстановлением сети.
